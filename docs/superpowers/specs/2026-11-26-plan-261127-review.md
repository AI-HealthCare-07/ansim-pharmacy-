### Task 4 (진료기록 PDF): "그대로 태운다"가 성립하지 않음 ❗

- 업로드(`save_upload`)는 **사진만** 글자 읽기·가림을 한다. PDF는 저장만 하고 상태가 `UPLOADED`에 머문다.
- 구조화 API는 `status = EXTRACTED`이고 `ocr_raw.lines`가 있어야 동작한다. 저장 함수 `update_ocr_quality`는 `extraction_method='IMAGE_OCR'`로 고정돼 있다.
- 따라서 "pymupdf 추출 → `pii_mask` → `ocr_raw` 저장 → `EXTRACTED`" 경로를 **새로 짜야** 한다 (1시간 안에 하기 빠듯).
- 구조화 스키마(`StructuredDoc`)는 처방전 한 장 기준이다. 진료기록은 여러 날짜·여러 병원이 섞이므로 약마다 조제일(`dispensed_date`), 과거 약은 기본 제외(`include_in_analysis=false`, DOC-007)가 필요한데 지금 스키마에는 없다. 오늘은 "뽑아낼 수 있는지 시험"으로 한정하면 괜찮지만, 결과 기록에 이 한계를 적어야 한다.

## 3. 빠진 위험과 예외 상황

### Task 0 (연결률 측정)
- **잴 대상이 섞여 있다.** "600종 중 금기·주의가 1건 이상 연결되는 비율"은 (가) 코드 체계가 이어지는지와 (나) 그 약에 원래 규칙이 있는지를 함께 잰다. 많은 약은 DUR 규칙이 **원래 없다**(정상). 이 숫자가 70% 아래여도 연결이 망가졌다는 뜻이 아닐 수 있다. 규칙 쪽에서 재는 연결률(schema.sql 점검 쿼리 2: `dur_rules` 성분코드가 `v_item_ingredients`에서 찾아지는 비율)을 **함께** 재야 판단이 가능하다.
- EDI 주성분코드가 없는 약(약가마스터 23,824건 중 2,422건)과 비급여·일반약은 성분코드가 없어 연결이 0이다 → 전문의약품만 따로 재자는 계획서 판단이 맞다.

### Task 1 (매칭)
- **다시 실행할 때:** `(document_id, line_no)` 고유 제약 때문에 두 번째 `/match` 호출은 실패하거나, 덮어쓰면 사용자가 이미 고른 약이 사라진다. 다시 실행 규칙(사용자 선택은 보존)을 정해야 한다.
- **EDI 동점:** `fn_match_by_edi`는 같은 EDI에 품목이 여럿이면 모두 1.000으로 돌려준다 → 격차 0이라 자동 확인이 안 된다. 의도라면 적어 두고, 아니면 이름 점수로 순위를 가린다.
- **EDI 오독:** OCR이 EDI 숫자를 잘못 읽어 다른 실제 약과 정확히 맞으면 1.000으로 자동 확인된다. 계획서가 성분명을 모든 약에 보여 주는 것으로 대비하고 있으나, EDI 결과 이름과 OCR 이름이 크게 다르면 자동 확인에서 빼는 교차 확인이 없다.
- 구조화 결과에 약이 0개인 문서, `edi_code`가 9자리가 아닌 값(CHECK 위반) 처리.

### Task 2·3 (확인)
- 확인 완료 뒤(`CONFIRMED`) 약 수정 요청을 막는지. 진단명 수정은 이미 `STRUCTURED`·`MATCHED`에서만 허용한다.
- 원본 삭제 순서: DB는 비웠는데 파일 삭제가 실패하면 파일이 남는다. `deletion_logs.storage_paths`로 다시 지울 수 있게 되어 있으나 앱 쪽 재시도가 없다.
- 원본 삭제 때 `ocr_raw`도 지워지므로, 확인 완료 뒤에는 구조화를 다시 할 수 없다(의도된 동작, 화면에서 막아야 함).
- 사진은 지금 인증 없이 `DEMO_USER_ID=1`로 동작한다. 썸네일 주소가 문서 번호만으로 열리면, 로그인 도입(12/7) 때 소유자 확인을 꼭 넣어야 한다.
- 이미 있는 예외: 가림 후 개인정보가 남은 사진(`PII_RESIDUAL`)은 상태가 `EXTRACTED`인데 `ocr_raw`가 비어 있어서 구조화 요청이 "글자 읽기가 끝난 문서만…"(409)으로 답한다. 이유가 틀린 안내다.

### 질문 1. "잘 모르겠어요" 약 → **A. `confirmed_by`에 `UNKNOWN` 추가** (2026-11-26 결정)

- `document_items.confirmed_by` 허용값을 `AUTO`·`USER`·`UNKNOWN`으로 넓힌다(제약 1줄 변경, 새 컬럼 없음).

- 함께 고칠 문서: 기획서 DOC-005("모두 확인해야" 문구), API 명세 D4(요청값)·D6(409 조건), schema.sql `ck_items_confirmed_by`, 결정 기록.

  **"그래서 이 약과 다른 약을 함께 먹어도 되는지는 살펴보지 못했어요"**를 적는다(병용금기 확인에서도 빠지기 때문).

### 질문 2. 자동 확인 규칙 → **C. 섞어서 쓰기** (2026-11-26 결정)

- **보험코드(EDI) 일치 + 0.7 이상** → 서버가 자동 확인(`confirmed_by='AUTO'`), 화면 표시 "보험코드로 약 이름 확인". 기획서 DOC-005 그대로.
- **이름 검색으로 1등 0.7 이상 + 2등과 0.15 이상 차이** → 1등 후보를 **미리 골라 두기만** 한다(`matched_item_seq`는 채우되 `confirmed_by`는 비움).
  사용자가 성분명을 보고 [모두 맞아요] 한 번으로 확인 → `confirmed_by='USER'`.
- 그 밖의 약(점수 낮음·동점·후보 없음) → 미리 고르지 않음, 후보 + 검색창으로 사용자가 고르거나 "잘 모르겠어요"(`UNKNOWN`).
- 이유: 자동 확인 표시가 붙은 약은 거의 틀리지 않게 지키고(OCR 잡음 질의 정밀도 96.8%, 성분이 같은 다른 제품으로 잘못 연결된 사례 있음),
  하나하나 고르는 수고는 줄인다. 이름으로 찾은 약의 최종 확인자는 사용자로 남는다.
- 함께 고칠 것: 계획서 Task 1·3(자동 확인 정의, "대부분 자동 확인" 서술), 11/26 일지의 규칙 이름("자동 확인" → "미리 선택"),

- 남은 판단(개발자 몫): [모두 맞아요]를 D4 여러 번 호출로 할지, 일괄 요청 하나로 할지.
