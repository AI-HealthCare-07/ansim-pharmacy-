1. 금기·주의 연결률(DUR 연결률)을 숫자로 잰다. 가장 큰 기술 위험이라 아침에 먼저 한다.
2. 구조화된 약을 의약품 DB에 연결하는 매칭 API를 만든다(EDI 우선, 자동 확인 규칙 적용).

완료 기준: 가상 처방전 1장을 올리면 확인 화면에 약 목록이 "자동 확인 / 확인 필요"로 나뉘어 보이고,
고르거나 "잘 모르겠어요"를 누르면 DB에 저장된다.

## 오늘 지킬 원칙 (11/26 결정)

- **테스트용 데이터(v2_test)는 쓰지 않는다.** 오늘의 측정·조정은 모두 개발용(v2, 600종)으로만 한다.
  테스트용은 규칙이 확정된 뒤(12/21 정량 검증) 한 번만 채점한다.
- **금기·주의 정보는 정확 조회다.** 약 코드(품목기준코드·EDI·성분코드)로 찾아 식약처 원문 그대로 보여 준다.
  벡터 검색(RAG)은 쓰지 않는다. RAG는 12/10 "생활 수칙"에만 쓴다.
- **외부 LLM은 Claude 하나.** 임베딩은 로컬 모델(12/10). OpenAI 등 다른 API는 쓰지 않는다.
- **새 테이블을 만들기 전에 schema.sql부터 본다.** 이미 있는 테이블과 함수를 쓴다.
- **사용자 화면에는 "DUR"을 쓰지 않는다.** 화면 용어는 "나에게 맞춘 의약품 정보"(MED-016).

## Task 0. 시작 점검과 DUR 연결률 측정 (오전, 1시간)

목표: 금기·주의 정보가 처방 약의 몇 %에 실제로 연결되는지 숫자로 안다.

- `docker compose ps postgres`로 DB 확인 (노트북을 덮었다 열었으면 Docker부터).
- schema.sql에서 금기·주의 관련 테이블(`dur_rules`, `drug_warnings`, `medicine_edi_codes` 등)과
  사용자 테이블(`users`, `user_profiles`)의 구조를 `\d`로 확인한다. Task 1~3이 이 구조를 쓴다.
- 개발용 v2의 600종 중, 성분 기준으로 금기·주의 정보가 1건 이상 연결되는 약의 비율을 잰다.
  가능하면 전문의약품만 따로도 잰다.
- 결과를 `docs/review/dur_link_rate_261127.md`에 남긴다.

판단 기준:
- 70% 이상: 계획대로 진행.
- 그보다 낮으면: 성분명(`item_ingr_name`) 문자열 보완 연결을 검토하고, 시연 처방은 연결되는 약 위주로 고른다.
  이 판단은 결정 기록에 남긴다.

## Task 1. 약 매칭 API (오전~점심, 1.5시간)

목표: 구조화 결과(`structured_json.drugs`)의 약마다 의약품 DB 후보를 붙여 `document_items`에 저장한다.

- 순서: EDI 코드가 있으면 `fn_match_by_edi` 먼저, 없거나 실패하면 `fn_search_medicines`.
- 자동 확인 규칙(11/26 확정): 1등 0.7 이상 **그리고** 2등과 0.15 이상 차이. 수출용 제외(함수에 반영됨).
- 후보는 최대 3개, 각 후보에 **성분명**을 함께 담는다(확인 화면 표시용).
- 1등 점수가 낮은 후보(0.7 미만)는 미리 선택하지 않는다.
- 상태: `MATCHED`. 저장은 `app/repositories/document_repository.py`에 SQL로 추가한다(ORM 모델 새로 만들지 않음).
- `document_items`의 실제 컬럼은 Task 0에서 확인한 구조를 따른다.

완료 기준: 7번에서 정리한 가상 처방전 문서에 `POST /api/v1/documents/{id}/match` → 약마다 후보와 자동 확인 여부가 저장됨.

## Task 2. 확인·수정 API (오후, 1시간)

목표: 확인 화면이 쓸 데이터를 한 번에 내려주고, 사용자의 선택을 저장한다.

- `GET /api/v1/documents/{id}/review`: 약마다 OCR이 읽은 이름, 자동 확인 여부, 후보(이름·성분명·점수),
  진단명, 진료일을 화면에 바로 쓸 수 있는 모양으로 내려준다.
- `PATCH /api/v1/documents/{id}/items/{item_id}`: 후보 선택, 또는 "잘 모르겠어요" → 상태 `확인 불가`.
  확인 불가 약은 나중에 안내서 하단에 "이 약은 확인하지 못했어요. 약사에게 꼭 물어보세요"로 표시한다(11/26 결정).
- 사용자 정보는 새 테이블을 만들지 않는다. 나이는 `users.birth_year`, 건강정보는 `user_profiles`를 쓴다.
  시연용 고정 사용자(user_id 1)의 출생연도를 시연 시나리오(68세)에 맞춰 둔다.
- 확인 완료 시 원본 파일 즉시 삭제(SYS-001 "확인 완료 시 즉시")는 이 API에 붙인다.

완료 기준: 리뷰 조회 → 한 약 선택, 한 약 "잘 모르겠어요" → DB 상태가 맞게 바뀜.

## Task 3. 확인·수정 화면 (오후, 2시간)

목표: 디자인 시안 3번(앱형)을 바탕으로 실제로 동작하는 화면 한 장.

- 기준 디자인: `docs/review_compare.html`의 시안 3. 시안 1·2는 비교용으로 남겨 둔다.
- 화면 구성:
  - 위: 진행 단계 표시, 사용자가 올린 사진 썸네일.
  - 가운데: 약 목록. **대부분은 자동 확인**(처방전에 흔한 표기는 v2 평가에서 98% 자동 확인)이라
    자동 확인 약은 접힌 목록으로 짧게 보여 주고, "확인 필요" 약만 펼쳐서 후보를 고르게 한다.
  - 모든 약에 성분명을 함께 표시한다(OCR 오타가 다른 실제 약 이름이 되는 경우 대비).
  - 아래: [확인 완료] 버튼, 확인 필요 약마다 [잘 모르겠어요].
- 사진은 **본인이 올린 원본을 본인에게만** 보여 준다. 사진 속 글자를 칠하는 기능(이미지 가림)은 오늘 하지 않는다.
  가림은 저장·전송용이고, 본인이 자기 사진을 보는 것은 문제가 아니기 때문이다.
  발표·스크린샷에는 가상 문서 사진만 쓴다.
- 색(11/26 결정, 대비 확인 완료):
  - 배경 미색 #FDFBF7, 연한 민트 #D2F2E8, 본문 글씨 차콜 #2C3E50 (10.6대 1)
  - 주 버튼: 아쿠아 민트 #55C1B8 바탕에 **진한 글씨 #1F2D2B** (6.6대 1). 흰 글씨는 2.2대 1이라 쓰지 않는다.
  - 경고 배지: 코랄 #FF8A65 바탕에 진한 글씨 #1F2D2B (6.2대 1).
  - 진한 초록·남색 조합은 쓰지 않는다(특정 병원 CI와 비슷해 보임).
- 기술: FastAPI가 제공하는 HTML 한 장 + 순수 JavaScript. 별도 프론트엔드 프레임워크는 12/3 화면 연결 때 다시 판단한다.

완료 기준: 가상 처방전 1장으로 화면을 열어 고르고 [확인 완료]까지 누르면 Task 2의 상태가 저장됨.

## Task 4. 진료기록 PDF 파싱 시험 (오후, 1시간)

목표: 트랙 A(글자가 든 진료기록 PDF)에서 진단명·진료일·처방 약을 뽑아낼 수 있는지 확인한다.

- 시험 파일: 개인정보가 없는 PDF만. 가상 데이터의 진료기록(M) 형식을 PDF로 만든 것이나, 비식별 처리한 PDF.
  본인·가족의 실제 진료기록은 프로젝트 밖 암호화 폴더에 두고, 가림 전에는 Haiku에 보내지 않는다.
- pymupdf로 글자를 뽑고 → 가림(`pii_mask`) → Haiku 구조화(`structuring`)를 그대로 태운다.
- 결과와 실패 사례를 `docs/review/pdf_parse_261127.md`에 기록한다.

## 데이터 최신성 (기획서 DAT-001 보완안, 오늘은 기록만)

- 모든 의약품 데이터와 안내에 **출처와 기준일을 표시**한다(MED-004). 이미 있는 `data_versions` 테이블을 활용한다.
- 갱신은 지금 단계에서 **수동 스크립트**로 한다(`scripts/ingest_data_go_kr.py`).
- "기준일이 오래되면 경고" 규칙은 **출처별 실제 갱신 주기를 확인한 뒤** 정한다.
  DUR 성분 정보는 2026.6 고시라 일괄 90일 기준을 쓰면 모든 화면에 경고가 뜬다.
- 자동 동기화(예약 실행)는 배포 서버가 생긴 뒤(12/14 배포 주간 이후)에 검토한다.
  지금 DB는 로컬 Docker에 있어 외부 예약 실행(GitHub Actions 등)이 접근할 수 없다.
